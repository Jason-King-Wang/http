我會把這個專案講成一套多步驟 Agentic workflow：上游資料不穩定，所以先做候選池、來源標記、LLM handoff、驗證與報告；模型建議和實際執行被刻意分開，輪轉週只是 shadow overlay，這就是 guardrailing 與 human-in-the-loop。

Architecture

  • Shioaji / web external pool 收斂成 merged AB candidate pool。
  • LLM 只讀合併候選池與 StockModelVault current rules，輸出 source = llm_vault_direct_preselect。
  • repair / validate / annotate / daily output 逐步落地，避免模型輸出直接進入發布層。
  • rotation regime 欄位寫入報告與 dashboard，但不能改 AB hard rule、候選池分數、實際買法或券商狀態。
  • 每日輸出同步到 Obsidian、public dashboard、Email 通知與後續 sell model bridge。

Done

  • 建立 AB 大候選池合併流程，整合內部候選、外部掃描、Shioaji API 與網路候選來源。
  • 建立 LLM 預選 handoff、輸出修復、schema 驗證與文字品質修復腳本。
  • 建立快速輪動週 precheck 與 shadow mode 語義，避免誤把風險燈號當成實際交易命令。
  • 產出每日 Markdown / JSON / CSV 與公開 dashboard 可讀資料。
  • 保留 applied_rule_ids、selection_reason、rotation traceability，能回頭查每檔標的為什麼被選。

Remaining Work

  • 把 Email approval / dashboard acknowledgement 做成正式人工確認 gate。
  • 補更完整的失敗情境 replay：網路池失敗、LLM 欄位缺漏、日期錯置、舊 latest fallback。
  • 若未來接實際券商執行，必須新增獨立 execution service，不能讓 AB pipeline 直接下單。
